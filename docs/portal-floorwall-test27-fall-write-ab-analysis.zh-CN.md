# 第27轮：fall 单因子修复的运行态与视觉因果验证

## 1. 结论

本轮成功：用户报告实验组已经感觉不到原先地板→墙面穿越后的延迟粘滞；日志同时证明原生通知/写入生效、两端fall一致、延迟空中预测误差及Reset消失、origin历史恢复正常插值。现在可把“入口fall峰值残留造成两端预测状态分离”从强候选提升为**本测试场景延迟空中粘滞的已验证主要原因**。

不是所有穿越问题都已经解决：提交后的第一个tick仍有一次fall比较误差和短暂的既有Reset；A组两次卡住是另一类异常样本；实验开启后的墙门/上下循环回归尚未在本文件中得到覆盖。下一步应收敛和做基线回归，不继续堆镜头补偿。

## 3. 测试分组和异常样本

A开启实验前：capture9–15 / txn7–13，共7次地板→墙面。B：capture16–20 / txn14–18，共5次。开关于第23479行切为1，最后32735行关闭；正常时间倍率、预测和插值保持开启。

### 两次卡住

capture9/txn7和capture15/txn13最符合用户描述：服务端连续40个命令没有server-walk-pre，确切fall caller计数为0，origin原生插值changed=0，服务端velocityZ保持不变，最后作用域以dead-or-movetype结束。两次均enabled=false、applied=0，不能归因于实验性fall写入。

它们必须排除出正常空中运动对比，不能因为capture-complete就算穿越正常，也不能宣称本轮修好了卡模型。日志只支持“服务端没有推进到已监测的FullWalkMove/fall更新处”；缺少碰撞/实体证据，尚不能确定具体模型或哪个早退分支。

capture14/txn12虽然八阶段配对完整，但窗口内未记录自然落地，后续dead-or-movetype结束，Reset明细还达到48条上限、丢弃5条。将其保留为可分析空中窗口，同时做额外剔除的敏感性检查，避免特殊尾段左右结论。

### 门位与回归覆盖

前两次B（capture16/17）仍是A的同一对门。第26364、26411、26488行有重放门记录，后三次B在重放后执行，因此不能声称全部5次B都是严格同门位复现。前两次同门位已足以复核核心因果链，后三次提供额外门位样本；无需为本轮因果结论重测整组。

6次墙门类窗口全部发生在实验开启前。文件末尾2次普通下落则enabled=true，但未发生穿越，因此没有绑定/写入，符合非全局接管下落的边界。不能把它们代替“穿越后落地伤害”和“开启实验后的墙门”验收。

## 4. 写入和网络变更通知真实生效

启动第6行：Hook installed=true、唯一updateMatches=1、原getter指纹有效、exactCallerRva=0xFC839。18次绑定均成功，没有绑定拒绝。

代表capture16 / txn14：

- 第23674行提交cmd8673：fallBefore=679.999878，moveZ=39.8900146，写入candidate=-39.8900146，notifyCalled/dirtyObserved/applied/readback均true。
- 第23713行原生比较已经看到网络值net=-39.906555，而预测仍是旧值706.666504；网络值与刚写入的负fall相符（量化差约0.01654）。这既是变更进入网络/客户端路径的证据，也是提交瞬间仍有一次预测对齐工作的证据。

## 5. A/B因果链

排除两次卡住，A有5个可分析空中窗口；B有5次正常落地窗口：

| 指标 | A：关闭 | B：开启 |
|---|---:|---:|
| 同cmd有效空中配对 | 111 | 110 |
| 命令结束fall不一致 | 105/111 | 0/110 |
| 延迟空中fall预测误差记录 | 100 | 0 |
| 延迟空中Reset明细 | 至少95 | 0 |
| origin夹取明细 | 222/229 | 0/127 |
| origin正常发生变化 | 7/229 | 127/127 |

A的95条延迟Reset全部有同frame/tick、先发生的fall误差前驱；由于capture14丢了5条Reset明细，95仅是明确观察到的下界。B五次Reset明细均未丢弃，故零结果不是日志上限或日志缺失。

B的127条延迟origin明细为10条Interval、117条Hermite，全部changed；没有Clamped。A的6个fall一致命令来自capture14后段新下降速度追上旧峰值，不是控制组普遍恢复。

更严格地只选同门位且自然落地：A capture10–13对比B capture16–17：

- A：72个空中命令全部fall不一致，68条延迟fall误差对应68条延迟Reset，158条origin明细全部夹取且不变。
- B：40个空中命令全部fall一致，延迟误差/Reset为0，47条origin明细全部正常变化。

因此改善不依赖两次卡住、特殊capture14尾段或后3次B重放门。与用户“已经感觉不到粘滞”的反馈方向一致，形成单因子因果证据。

全捕获窗口的finalTotal冻结统计：上述4次严格A分别360.888/182.435/386.083/333.693ms；B五次8.401/0/0/0/4.897ms。这是按引擎帧时累计的视图不变指标，不是“整次游戏卡死时长”，也不能把多个片段当成一次连续停顿。

## 6. 仍然存在的边界

1. 每次B在提交后的第1个tick仍有一条fall预测误差；Reset主要集中于前2tick，另两次有落地tick的Reset。消失的是之后反复发生的空中错误链，不是全程零Reset/零预测误差。当前没有相应主观症状，不为抹平日志而屏蔽原生纠错。
2. 2次卡住另立碰撞/出口有效性问题；本轮不扩展修复，不能承诺开启fallfix就不会卡住。
3. 本轮开启实验后的墙门走/跳/高速、上下3500循环未覆盖，暂不可宣布所有旧基线无劣化。
4. 普通下落未见fall写入/此类fall误差，证明作用域没有直接外溢；没有健康值/伤害事件证据，仍需针对穿越后立刻落地的冲击/伤害做安全回归。
5. 只验证当前二进制、单人localserver与记录速度范围；不外推多人服务器、所有运动类型或所有地图模型。
